```text
Status: Approved with copy amendment
Version: 1.1
Date: 2026-07-12
```

## 0. 设计结论

建议方向总体合理：管理端应由“功能平铺”改为“学习工作台 / 内容管理 / 系统治理”三组，并从用户任务而不是开发批次出发组织页面。

本轮建议进一步明确以下结论：

1. `采集`、`待审核`、`复习`构成学习处理主链，`总览`负责提示下一步行动。
2. `题库`与`错题`只管理正式内容；草稿创建和人工审核从这两个页面移出。
3. `AI`保留为只读治理入口，`AI Run 审计`作为其重要二级入口继续保留。
4. `/manage/jobs`当前没有真实队列能力，应退出一级导航；不以占位页面暗示系统具备后台任务能力。
5. `/manage/settings`当前没有可保存设置，应暂时退出一级导航。长期信息架构仍为其预留“系统治理”位置，待存在真实设置能力后再恢复入口。
6. 旧 `/manage`仍承载登录和历史内容维护，不能在本次 UI 收束中直接删除；新工作台顶栏的“旧管理面板”入口应移除或降为明确命名的历史内容入口，并另行评估迁移。

## 1. 当前 UI 问题分析

### 1.1 导航按模块平铺，缺少任务顺序

当前侧栏依次列出总览、待审核、题库、错题、采集、复习、科目、附件、AI、任务、设置。该顺序同时混合：

- 日常动作：采集、审核、复习。
- 内容对象：题目、错题、科目、附件。
- 运维与治理：AI、任务、设置。
- 已启用能力与占位能力。

用户无法从导航结构判断“现在该做什么”和“内容最终存在哪里”。采集位于错题之后，也弱化了“采集 -> 审核 -> 正式内容 -> 复习”的处理链。

### 1.2 开发批次成为用户可见信息

页面标题、说明和总览状态中仍出现 `Batch 1`、`Batch 3`、`Batch 4`、`Batch 8`、`Batch 11`、`MVP`、`占位`、`后续启用`等表达。这些文案描述系统如何被开发，而不是用户如何完成学习任务。

同时，总览仍展示“尚未接入”等已经失真的阶段性文案，削弱了页面作为长期入口的可信度。

### 1.3 页面职责交叉

- `/manage/drafts`同时承担审核队列与手工创建题目草稿。
- `/manage/mistakes`同时承担创建草稿、审核草稿和正式错题列表。
- `/manage/capture`拥有完整图片采集流程，但入口、处理状态、失败恢复和已转换记录之间的层级不够清晰。
- `/manage/jobs`与`/manage/settings`仅解释未来能力，却占据主导航位置。
- `/manage/ai`同时展示业务 Run、Provider、健康、用量、费用、统计与技术日志，但页面缺少稳定的长期层级。

### 1.4 视觉语言适合公开端，不完全适合高频管理

现有浅蓝绿色、半透明表面和柔和阴影符合低压力学习氛围，应继续保留。但管理页面大量使用大圆角、大内边距和独立卡片，造成：

- 同屏可比较信息偏少。
- 状态、筛选、动作和列表之间不够紧凑。
- 空状态与占位说明占据过多首屏空间。
- 各页面自行实现表格、状态颜色、表单容器，反馈模式不一致。

### 1.5 当前实现证据

| 现状 | 当前文件 |
| --- | --- |
| 导航为 11 个平铺入口 | `src/app/manage/components/manage-sidebar.tsx` |
| 工作台统一受 `AuthGate` 保护 | `src/app/manage/(workspace)/layout.tsx` |
| 顶栏保留“旧管理面板”入口 | `src/app/manage/components/manage-topbar.tsx` |
| 总览仍以 Batch 和占位状态组织 | `src/app/manage/(workspace)/dashboard/page.tsx` |
| 草稿页混合审核与手工创建 | `src/app/manage/(workspace)/drafts/components/draft-workspace.tsx` |
| 错题页混合创建、草稿、正式记录 | `src/app/manage/(workspace)/mistakes/components/mistake-workspace.tsx` |
| Jobs 与 Settings 为未来能力占位 | `src/app/manage/(workspace)/jobs/page.tsx`、`settings/page.tsx` |
| AI 已包含治理快照和 Run 审计入口 | `src/app/manage/(workspace)/ai/page.tsx`、`ai/runs/page.tsx` |

## 2. 新信息架构

### 2.1 业务模型

管理端围绕一条长期学习闭环组织：

```text
采集输入 -> 人工审核 -> 正式题目 / 正式错题 -> 到期复习 -> 学习反馈
                    \-> 附件、科目与知识点提供支撑
                    \-> AI 提供受控辅助和治理审计
```

页面分为三层：

| 分组 | 用户问题 | 页面 |
| --- | --- | --- |
| 今日学习 | 我现在要做什么？ | 今天、收进来、待确认、温习 |
| 我的资料 | 我收好的学习内容在哪里？ | 题目册、错题本、学科角、资料袋 |
| 小助手 | 小助手最近工作得顺不顺利？ | AI 小助手；设置在有真实能力前不显示 |

### 2.2 公开首页与管理端边界

| 区域 | 负责 | 不负责 |
| --- | --- | --- |
| 公开首页 | 内容展示、公开阅读入口、轻量学习入口、品牌体验 | 数据 Dashboard、AI 状态、任务队列、私有复习详情、管理操作 |
| 管理端 | 高密度工作流、私有状态管理、内容操作、复习处理、AI 治理 | 品牌营销、公开内容编排展示、面向访客的解释性体验 |

边界规则：

- 未登录访客不应在公开首页看到管理统计或管理失败状态。
- 管理员可从一个轻量入口进入工作台，但管理快捷操作不与公开导航并列铺开。
- 管理端继续由现有 `AuthGate` 和后端权限共同保护；本设计不改变权限模型。
- 公开端维持低密度，管理端提高密度，两者共享品牌色而不强求共享页面组件。

## 3. 导航方案

### 3.1 推荐结构

```text
今日学习
  今天        /manage/dashboard
  收进来      /manage/capture
  待确认      /manage/drafts
  温习        /manage/review

我的资料
  题目册      /manage/questions
  错题本      /manage/mistakes
  学科角      /manage/subjects
  资料袋      /manage/attachments

小助手
  AI 小助手   /manage/ai
```

条件入口：

- `设置 /manage/settings`：保留路由，不进入当前一级导航；出现至少一个真实、可读取或可保存的设置项后再加入“系统治理”。
- `处理记录 /manage/ai/runs`：保留为 AI 小助手页内二级入口，不重复占据侧栏。

退出一级导航：

- `任务 /manage/jobs`：当前无队列、worker 或任务 API。路由可暂时保留兼容，但侧栏、总览和日常入口均不展示。
- `旧管理面板 /manage`：从工作台顶栏移除笼统入口。由于它仍有历史内容管理能力，本阶段不删除路由；后续应以“历史内容管理”等准确名称单独评估迁移和收口。

### 3.2 导航行为

- 桌面端显示分组标题，组内顺序固定；不按 Batch、数据量或最近开发内容动态排序。
- 当前路由的详情页也应激活所属一级入口，例如 `/manage/ai/runs`激活“AI”，`/manage/mistakes/[id]`激活“错题”。导航项应显式配置匹配规则，不用 `/manage`的宽泛前缀匹配推断归属。
- 移动端固定采用抽屉导航：顶栏显示当前页面标题和菜单按钮，抽屉内呈现与桌面一致的三组导航，选择页面后自动关闭并恢复合理焦点。
- 移动端不使用横向滚动标签平铺全部入口。
- 导航项不显示“即将推出”徽章。未启用能力直接不展示。
- 数量徽章只展示可由现有接口稳定获得、且能帮助决策的数量；无法确认时不显示 `0`或占位符。

## 4. 页面职责矩阵

| 页面 | 当前职责 | 目标职责 | 收束动作 |
| --- | --- | --- | --- |
| `/manage` | 登录入口；历史笔记、博客、音乐、站点设置、安全、审计等旧管理面板 | 管理身份入口与历史能力过渡页，不再与学习工作台形成两个并列主面板 | 保留登录和未迁移能力；移除新工作台中的“旧管理面板”主入口；历史能力迁移另立任务 |
| `/manage/dashboard` | Batch 入口索引和占位状态清单 | 日常工作总览：下一步行动、真实待处理状态、主要入口 | 移除 Batch、MVP、尚未接入和 Jobs/空设置入口；只用现有真实数据或无数字快捷入口 |
| `/manage/capture` | 图片上传、OCR、AI 草稿、转换及采集列表 | 统一采集入口与处理状态追踪 | 首屏明确“新建采集”和“最近采集”；将手工题目草稿录入作为采集方式迁入，图片链路不改变 |
| `/manage/drafts` | 题目草稿审核队列 + 手工创建题目草稿 | 审核中心，集中处理待确认内容 | 移除创建表单；按内容类型或状态组织题目草稿、错题草稿；保留人工确认、修正、拒绝语义 |
| `/manage/questions` | 正式题目列表与状态筛选 | 正式题库管理 | 保持正式内容边界；统一筛选、状态、空态和行操作，不承担草稿创建或审核 |
| `/manage/mistakes` | 从题库创建错题草稿 + 待审核草稿 + 正式错题 | 正式错题管理 | 创建入口迁到采集，待审核列表迁到审核中心；本页只展示、筛选和进入正式错题详情 |
| `/manage/review` | 到期复习队列、评分提交、历史记录 | 今日复习工作区 | 保留单一任务焦点；突出到期项、提交反馈和完成状态，不承担复习统计 Dashboard |
| `/manage/subjects` | 科目、章节和知识点维护 | 学习分类管理 | 保持现有职责；作为内容管理的支撑资料，统一列表和表单容器 |
| `/manage/attachments` | 私有附件上传、列表与详情 | 学习附件库 | 保持现有职责；强化来源、关联状态和上传反馈，不宣传未启用 OCR 能力 |
| `/manage/ai` | Run 审计入口、Provider 状态、健康快照、用量费用、调用统计与日志 | 只读 AI 治理中心 | 按“运行审计 -> 服务状态 -> 用量费用 -> 技术日志”排序；保留 Run 审计；不增加在线配置或探针 |
| `/manage/ai/runs` | 业务 Run 列表、详情和人工流转 | AI 运行审计二级页 | 保留独立页；去除 Batch 文案，使用 AI 面包屑或返回入口；侧栏归属 AI |
| `/manage/jobs` | 无真实任务能力的说明占位 | 不作为当前产品页面 | 从所有主要入口隐藏；不新增队列能力；是否删除路由由兼容性扫描后决定 |
| `/manage/settings` | 无保存能力的设置归属说明 | 未来真实系统设置入口 | 当前从主导航隐藏；不把 AI 只读状态误称为设置；有真实能力后再启用 |

### 4.1 关键职责迁移

为避免“只是换标题，混合职责仍然存在”，下一阶段应按以下归属调整现有 UI：

| 当前模块 | 目标位置 | 原因 |
| --- | --- | --- |
| 手工创建题目草稿 | `/manage/capture` 的“手工录入”采集方式 | 它是输入动作，不是审核动作 |
| 错题草稿创建 | `/manage/capture` 的“从题库记录错题”采集方式 | 它是错题进入系统的入口，不是正式错题管理 |
| 题目草稿审核 | `/manage/drafts` | 审核中心统一承载待确认内容 |
| 错题草稿审核 | `/manage/drafts` | 正式错题页不再混入草稿状态 |
| 正式错题列表 | `/manage/mistakes` | 该页面只代表已确认学习资产 |

上述迁移复用现有 API 和业务动作，不改变数据模型。第一阶段可保留现有详情 URL，避免把 UI 收束扩大为路由和契约重构。

审核中心第一阶段采用单一列表与类型筛选：

```text
全部 | 题目草稿 | 错题草稿
```

列表统一展示内容类型、内容摘要、来源、当前状态、创建时间和“查看并审核”操作。不在首屏上下堆叠两套完整审核列表。

采集页第一阶段采用三种采集方式，选择后才展开对应工作区：

```text
上传图片 | 手工录入题目 | 从题库记录错题
```

三种方式共享入口层级，不强行共享字段或合并成一个大型表单。

### 4.2 总览数据边界

- 只调用现有接口，不新增 Dashboard 聚合统计接口。
- 不为计算数量而拉取全量列表。
- 现有接口不能低成本提供可靠数量时，只展示入口和状态描述。
- 请求失败不得显示为 `0`；未知值不展示数字徽章。
- 总览失败不得阻断进入采集、审核或复习等核心页面。

## 5. 视觉系统与组件规范

### 5.1 视觉原则

保持：

- 浅蓝绿色作为品牌强调色。
- 轻透明表面、柔和边框和低压力学习感。
- 公开端现有低密度、内容优先的体验。

管理端调整：

- 列表、筛选和状态区优先使用紧凑行布局，不把每条信息都做成卡片。
- 管理内容面板圆角统一为不超过 `8px`，减少大面积圆角容器的层层嵌套。
- 页面纵向间距采用稳定层级：页面头、工具栏、数据主体、辅助说明。
- 成功、警告、失败、处理中和中性状态使用不同语义色，品牌色只用于选中态与主操作。
- 玻璃效果保留在工作区外壳和少量主表面；数据表、表单与状态反馈优先保证对比度和可读性。
- 空状态使用紧凑高度，首屏仍能看到筛选或主要动作。

### 5.2 组件审查结论

| 组件 | 当前判断 | 统一方案 |
| --- | --- | --- |
| `Sidebar` | 已有 `ManageSidebar`，但导航平铺且详情路由激活规则不足 | 作为管理端统一组件保留；增加分组数据模型、父路由匹配、桌面/移动行为 |
| `PageHeader` | 已有 `ManagePageHeader`，但 eyebrow 被用于 Batch 标签，标题偏大 | 作为管理端统一组件保留；eyebrow 仅用于稳定领域标签或面包屑，支持右侧动作和紧凑密度 |
| `EmptyState` | 全局组件偏公开端，管理页也存在大量临时文本空态 | 不直接强行统一公开端样式；增加管理端紧凑变体或 `ManageEmptyState`，统一 loading/empty/error/action |
| `Card` | 全局 `Card`绑定首页网格位置和动效，不适合管理端 | 不复用；管理端统一为轻量 `ManagePanel`，只处理边框、背景、间距和标题区 |
| `StatusBadge` | 当前无共享组件，各页面自行维护状态颜色和中英文 | 新增管理端统一组件；采用 `neutral/info/success/warning/danger`语义，不让业务状态直接决定 CSS |
| `DataTable` | 当前无共享组件，AI、旧管理页和列表各自实现 | 优先建立组合式表格外壳和样式，不建立 columns/data/filters 全包式内部框架；统一表头、行密度、横向滚动、空态、错误态和分页 |
| `FormPanel` | 当前无共享组件，多个页面重复表单外壳 | 建立 `ManageFormPanel`作为布局容器，统一标题、说明、错误、主次动作；不抽象字段业务和提交逻辑 |

### 5.3 推荐的管理端组件边界

```text
src/app/manage/components/
  manage-sidebar.tsx
  manage-topbar.tsx
  manage-page-header.tsx
  manage-panel.tsx
  manage-empty-state.tsx
  manage-status-badge.tsx
  manage-table.tsx
  manage-form-panel.tsx
```

约束：

- 这些组件只统一表现和交互骨架，不封装 API 请求。
- 页面或 route-specific workspace 仍持有数据加载、提交、权限和业务状态。
- 不把管理组件上移到全局 `src/components/`，除非已有两个以上非 manage 路由确实复用。
- 不创建万能 `Card`、万能表单 schema 或全局状态机。
- `ManageStatusBadge`只接受 `neutral/info/success/warning/danger`等语义 tone；各业务页面显式维护“业务状态 -> tone”映射。
- 表格能力以 `ManageTableContainer`、表格样式、空行和分页等组合单元为主，不要求所有页面适配统一列配置 API。

### 5.4 状态反馈规范

统一覆盖以下页面状态：

| 状态 | 呈现 |
| --- | --- |
| 加载中 | 保持工具栏和稳定容器尺寸，主体显示简洁加载状态 |
| 无数据 | 说明当前结果为空，并只给一个最相关的下一步动作 |
| 筛选无结果 | 保留筛选条件，提供“清除筛选”而不是引导创建新内容 |
| 请求失败 | 页面内错误提示 + 明确重试；toast 只作为补充 |
| 操作处理中 | 禁用当前动作并保留布局，不让按钮宽度变化 |
| 操作成功 | 就地更新状态，并以简短反馈确认结果 |
| 未启用 | 不在导航展示；不要用可点击的禁用按钮模拟未来能力 |

## 6. 文案规范

### 6.1 总原则

1. 用户可见文案采用温柔、轻松、可爱的中文，优先说“现在可以做什么”，减少“治理、审计、Provider、Run、Snapshot、Dashboard、状态流转”等技术词。
2. 可爱不等于幼稚：不用突兀角色昵称、夸张拟声词、连续感叹号或让失败显得不重要的玩笑。
3. 路由、代码名、API 字段、数据库状态和开发文档保持原名；可爱风只作用于用户会看到的标题、按钮、标签、提示与空状态。
4. 按钮使用轻柔动词，例如“选一张图片”“帮我读一读”“放进待确认”“再试一次”。
5. 错误、安全、费用和不可逆操作仍要准确。失败写“这次没有成功”，费用未知写“还没有费用记录，不代表 0”。
6. 空状态给出一个轻松但明确的下一步，不承诺未启用能力，不展示虚构数字。

## 7. 实施拆分建议

本设计获批后，应新建正式 `requirements.md` 与 `tasks.md`，经用户明确批准任务清单后再实施。建议拆成以下可独立验收的阶段，不在本轮执行：

### 阶段 A：导航与开发痕迹清理

- 将侧栏改为三组结构。
- 隐藏 Jobs 和空设置入口。
- 修正详情页父级激活规则和移动端导航。
- 移除 Batch、MVP、占位和旧管理面板文案。
- 不移动业务模块，不改 API。

### 阶段 B：管理端基础组件统一

- 收束 PageHeader、Panel、EmptyState、StatusBadge、DataTable、FormPanel。
- 先在一张低风险列表页验证，再逐页替换重复表现层。
- 不抽象业务请求、DTO 或表单字段。

### 阶段 C：页面职责归位

分为两批独立验收：

- C1 题目链：手工题目录入迁到采集；题目草稿审核留在待审核；题库只保留正式题目。
- C2 错题链：错题草稿创建迁到采集；错题草稿审核迁到待审核；错题页只保留正式错题。
- 第一阶段复用现有 API 和详情路由，避免契约扩张。

### 阶段 D：总览与 AI 长期布局

- D2：AI 按运行审计、服务状态、用量费用、技术日志重排。

### 阶段 E：视觉与浏览器验收

- 桌面和移动端核对导航、表格、表单、空态、加载、失败和长文本。

- 验证长 Provider 名称、长错误摘要和中英文混排不会溢出或遮挡操作。

## 8. 风险分析

| 风险 | 影响 | 缓解方式 |
| --- | --- | --- |
| 旧 `/manage`仍有独有能力，直接删除会造成功能丢失 | 高 | 本轮只移除新工作台中的旧入口；先做能力清单和独立迁移设计 |
| 草稿模块迁位后，详情 URL 与导航归属暂时不一致 | 中 | 第一阶段允许保留现有 URL，以侧栏父级激活和返回路径消除困惑；路由收束另立范围 |
| 审核中心聚合两类草稿后信息过载 | 中 | 使用内容类型筛选或分段，不把两套完整表单同时铺在首屏 |
| 总览为展示数量而产生多接口或全量请求 | 中 | 只复用已有轻量响应；禁止拉取全量列表计数；无稳定数据就展示入口 |
| 隐藏设置后，用户可能找不到现有真实设置 | 中 | 实施前先核对路由是否仍完全占位；真实能力保留准确入口，纯占位才隐藏 |
| 组件统一演变为大规模重构 | 中 | 组件只处理表现层；按页面逐步迁移，不改业务 hooks、API client 和 DTO |
| 玻璃效果在高密度表格中降低对比度 | 中 | 数据主体使用更实的背景和清晰边框，玻璃效果集中在外壳 |
| 状态颜色重构造成含义误判 | 中 | 先建立业务状态到语义 tone 的显式映射，保留原状态值和 API 契约 |
| AI 页面收束时泄露敏感字段或误导费用 | 高 | 保持只读边界；不展示 API key、authorization、cookie、secret、token、prompt、input summary、replay input 或原始 Provider 错误正文；未知费用不记为零 |
| Jobs 路由仍可直接访问，残留开发文案 | 低 | 一级入口先隐藏；路由删除或兼容提示须经引用扫描后另行决定 |
| 管理端密度提高后移动端操作拥挤 | 中 | 移动端使用分组菜单、横向表格容器和稳定动作区，并做真实浏览器验收 |
