## 目标（tasks.md / design.md D2 定版）

在 `review_item_service.py` 实现 `fixed_interval_v2` 调度语义，不得再留"二选一"：

- 失败 rating ∈ {0,1} → `repetitions=0`、`interval=1d`、`last_rating=rating`、`state=active`（lapse）
- 失败 rating = 2 → `repetitions=0`、`interval=2d`、`last_rating=rating`、`state=active`（温和 lapse 档）
- 成功 rating ∈ {3,4,5} → `repetitions+=1`；阶梯按自增后次数：1→3d / 2→7d / 3→14d / ≥4→30d
- 每次成功提交后立即评估 `repetitions>=4 AND last_rating>=4` → `state='mastered'`；rating=5 只影响 mastery 判定，不跳级
- `submit_review` 写入 `ReviewRecord.previous_state/new_state` 与 `item.last_rating`
- 保留既有乐观并发（F10：`expected_next_review_at` + `with_for_update` + ReviewConflict）

## 必办项（自 PR-05 独立评审 F-1 转入）

评审发现 F-1：migration 028 将存量行标为 `fixed_interval_v2`，但窗口期内 v1 service 仍按 v1 调度且失败也 `repetitions+=1`，导致这些行的 `repetitions` 不再等价于"自上次 lapse 的连续成功次数"，PR-06 上线后 mastery 可能提前误触发。

处置决定（Astra，2026-09-13）：**书面接受偏差，不做运行时重推导**。理由：
1. 受影响数据库仅为一次性隔离 scratch 实例（opencode/astra），无任何生产部署，窗口期"touched items"只存在于会丢弃的测试库；
2. Week 2 Gate 全链数据在 scratch 上以 v2 语义全新创建，不含窗口期污染；
3. rating 历史完整保留于 review_records，若未来真实环境出现同型偏差，可从历史重推导（评审已确认可推导性）。
该偏差与理由随本 PR 记录在案；若后续出现真实环境的 028→PR-06 窗口数据，必须在部署前重推导。
