# 需求：F4 前总工作夹

## 一、背景

现有前端重构已经拆成多个独立 workflow，但 F4 前的状态、审批、Gate 和用户决策点没有形成一份当前可执行的总合同。若直接分别执行，可能出现以下问题：

- 编辑器设计建立在尚未确定的路由或 Markdown 边界上；
- 公开会话优化隐式改变认证机制；
- 性能基线采集时仍包含已知认证噪音或即将变化的渲染实现；
- 单个子任务通过，但公开读取、管理员操作和生产构建没有形成整体闭环。

## 二、用户角色

- 未登录访客：读取公开博客、笔记和错题；
- 个人管理员：登录、编辑、管理、复习和使用 AI 辅助能力；
- 项目维护者：执行构建、测试、隔离验收、回滚和风险记录。

## 三、功能需求

### FFQ-REQ-01 统一基线

- 输入：当前源代码、AGENTS 规则、五个子任务组及已有浏览器探测；
- 处理：建立路由、渲染、编辑器、认证和性能的当前事实矩阵；
- 输出：唯一的依赖图、冲突清单、审批状态和证据位置；
- 失败处理：无法由源代码确认的内容保持 UNKNOWN，不用历史方案替代；
- 验收：`audit.md` 中所有关键断言有当前来源。

### FFQ-REQ-02 路由和权限所有权

- 输入：公开路由、管理路由、旧写作入口、导航链接及 AuthGate；
- 处理：确认长期 owner、兼容方式和公开/私有边界；
- 输出：保留、重定向、弃用或延后决策；
- 失败处理：未获产品决策时不得修改或删除路由；
- 验收：公开读取和管理员编辑路线都有明确 owner。

### FFQ-REQ-03 内容信任边界

- 输入：管理员、AI 和历史内容产生的 Markdown；
- 处理：以恶意夹具、SSR、hydration 和特殊渲染器验证隔离 PoC；
- 输出：go/no-go 结论和允许的结构/URL/特殊渲染边界；
- 失败处理：特殊渲染器不满足合同则使用惰性回退，不进入生产迁移；
- 验收：不存在使用旧渲染器作为 XSS 回退的路径。

### FFQ-REQ-04 编辑器能力合同

- 输入：note、blog、mistake 的现有编辑入口、字段、保存和预览行为；
- 处理：识别共享原语与必须独立的领域能力；
- 输出：最小提取方案或继续共存方案，以及单独实现清单；
- 失败处理：无法证明共用价值时不强制合并为 UnifiedEditor；
- 验收：错题一等字段和公开/私有权限没有被普通 Markdown 表单吞并。

### FFQ-REQ-05 会话状态分层

- 输入：公开页面和严格管理员页面的会话检查；
- 处理：在不弱化后端权限的前提下区分 optional 与 strict 状态；
- 输出：匿名公开页无预期 401 噪音，管理员控件和严格页面正常；
- 失败处理：认证机制合同未冻结时不得新增接口或迁移 hook；
- 验收：`get_current_admin`、AuthGate、写入、AI、上传和复习权限保持严格。
- G0 冻结：本阶段以当前 Cookie 会话为实现事实；仓库规则中的 Bearer/JWT 目标不在本任务组实现范围，任何对齐必须独立立项。

### FFQ-REQ-06 F4 输入包

- 输入：G2、G3、G4 的结论、残余风险、目标页面和验证边界；
- 处理：整理 F4 所需的 ready/empty/error 标记、合成数据、隔离构建、浏览器场景、样本和清理要求；
- 输出：一份可单独审批的 F4 输入包，不运行生产构建或性能采样；
- 失败处理：G3 或 G4 未通过时标记 BLOCKED，不伪造 F4 READY；
- 验收：明确区分“F4 输入齐备”与“F4 已执行/通过”。

### FFQ-REQ-07 用户决策门

- D1 输入：M6 当前能力、缺失 artifacts、deferred 路径观测缺口及作者/读者体验影响；
- D1 输出：用户已于 2026-08-16 选择“全部特殊适配器启用后再关闭 G2”；Mermaid、Markmap、Chart 任一未达到 `ENABLED_ISOLATED`，G2 即保持 BLOCKED；
- D2 输入：E1～E4 的编辑器字段、保存、预览、权限、复用收益和回滚证据；
- D2 输出：用户明确选择“最小共享原语 + 共存”或授权更大的统一编辑器后续任务；
- 失败处理：不得由代理替用户选择会改变内容能力或长期编辑体验的方向；
- 验收：决策、理由、影响和未授权范围同时记录在 `tasks.md`、`audit.md` 与 `validation.md`。

## 四、非功能需求

- 安全：公开 UI 状态不充当后端授权；`AUTH_BYPASS` 不参与验收。
- 兼容：旧链接、公开读取和管理员主流程必须有回归证据。
- 数据：只使用隔离数据库和确定性合成内容，不使用真实个人内容。
- 可维护：优先现有 SWR、Zustand、typed API 和组件模式，不新增状态库。
- 可回滚：每个源代码阶段有独立 diff、测试和回滚边界。
- 可审计：每个 Gate 必须在总 `validation.md` 和子 workflow 中记录。
- 决策最小化：只把内容能力与编辑器产品方向交给用户；技术实现细节由执行代理按证据收敛。

## 五、明确边界

- 不包含视觉 Token、导航外观、弹层或 Context Action 迁移。
- 不包含统一创作面板或 `/manage/create` 的产品实现。
- 不授权生产部署、真实数据迁移、路由删除或 Markdown 生产切换。
- 不执行 F4 的 readiness instrumentation、合成数据、生产构建或性能采样。
- 不实施 Bearer/JWT 迁移；F2B 只优化当前 HttpOnly Cookie 会话的 optional display-state。
- 不把五个子任务合并成一次不可审查的大提交。
- G0 只确认“当前实现、目标规则与不迁移边界已经清晰”；不确认 Cookie 与 Bearer/JWT 已经一致。

## 六、F4 前验收标准

- 五个子任务的依赖和审批状态一致，所有历史“下一项”已标为历史；
- G2 具有用户明确接受的产品边界，或诚实保持 BLOCKED；
- G3 证明匿名公开页无预期认证噪音，管理员严格权限不变；
- G4 具有字段、保存、预览、权限和回滚证据支持的编辑器方向；
- F4 输入包完整，但不宣称 F4 已执行；
- 所有失败进入风险清单或下一轮需求；
- F2B 浏览器验收涉及的临时账户、数据库和进程清理完成；
- 最终结论明确为 PASS、PARTIAL 或 BLOCKED，不使用模糊的“基本完成”。
