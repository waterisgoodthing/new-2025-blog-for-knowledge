# PR-14 — OCR Diagnostic and UI

Status: **NOT_STARTED**  
Risk: MEDIUM  
Gates: G0 (requirement/domain), G4 (recommendation)  
Dependencies: W4-00

## Objective

Establish OCR failure visibility, categorization, and retry flow. Produce a 10-sample baseline report and implement honest entry-point treatment based on actual success rate.

## Scope

**In scope:**
- Failure taxonomy and categorical logging
- Success/failure instrumentation
- 10-sample controlled baseline
- UI: loading → success | error(with category + retry) states
- Entry-point labeling or disabling if <80% success

**Out of scope (NOT_AUTHORIZED):**
- OCR pipeline rewrite or model replacement
- Candidate confirmation UI (PR-22)
- Background status tracking (PR-26)
- Multi-provider fallback logic

## Implementation Tasks

### 1. Failure taxonomy

- [ ] Define failure category enum in `backend/app/schemas/capture.py`:
  ```python
  class CaptureFailureCategory(str, Enum):
      PROVIDER_AUTH = "provider_auth"           # API key invalid, quota exceeded
      PROVIDER_TIMEOUT = "provider_timeout"     # Request timeout, network error
      INVALID_MODEL = "invalid_model"           # Model ID not found
      INVALID_RESPONSE = "invalid_response"     # Malformed JSON, unexpected structure
      SCHEMA_VALIDATION = "schema_validation"   # Response doesn't match expected schema
      IMAGE_FETCH = "image_fetch"               # Cannot fetch image from URL/storage
      IMAGE_FORMAT = "image_format"             # Unsupported format, corrupted image
      UNKNOWN = "unknown"                       # Unclassified error
  ```
- [ ] Add `failure_category` optional field to `CaptureOut` schema
- [ ] Update `CaptureRecognition` model to store `failure_category` (nullable VARCHAR)

### 2. Service instrumentation

- [ ] Wrap OCR service calls in `backend/app/services/capture_recognition_service.py` with categorical exception handling
- [ ] Map each exception type to failure category:
  - `AuthenticationError` → `PROVIDER_AUTH`
  - `TimeoutError`, `ConnectTimeout` → `PROVIDER_TIMEOUT`
  - `ModelNotFoundError` → `INVALID_MODEL`
  - `JSONDecodeError` → `INVALID_RESPONSE`
  - `ValidationError` from Pydantic → `SCHEMA_VALIDATION`
  - `ImageFetchError` → `IMAGE_FETCH`
  - `UnsupportedImageFormatError` → `IMAGE_FORMAT`
  - All others → `UNKNOWN`
- [ ] Log each failure with category, capture_id, and error message (sanitized, no secrets)
- [ ] Track success/failure counts (can be log-based grep-able metrics; no requirement for Prometheus)

### 3. 10-sample baseline

- [ ] Select or create 10 diverse test images:
  - 3 handwritten math problems
  - 3 printed text (Chinese/English mix)
  - 2 diagrams or charts
  - 2 edge cases (low contrast, rotated, partially obscured)
- [ ] Create `backend/tests/test_ocr_baseline.py` with 10 test cases
- [ ] Run controlled recognition attempts; record outcomes
- [ ] Generate `evidence/pr-14-ocr-baseline-report.md`:
  - List each sample with success/failure status
  - For failures: record category and error details
  - Calculate success rate: `successful / 10`
- [ ] Make entry-point decision:
  - If ≥8 success: entry remains visible without warning
  - If <8 success: add "experimental" label or disable entry
  - Document decision in report

### 4. UI implementation

- [ ] Update `src/app/capture/` (or wherever OCR entry lives) to show four states:
  - **Loading**: spinner with "Processing image..." text
  - **Success**: extracted content, proceed to draft
  - **Error**: error message with failure category (user-friendly translation), Retry button
  - **Empty**: "No content extracted" (distinct from error)
- [ ] Implement retry button:
  - Calls the same recognition endpoint with same capture_id
  - Shows loading state during retry
  - Increments attempt count (logged for analysis)
- [ ] Add entry-point treatment (based on baseline decision):
  - If experimental: add visible label "🧪 Experimental: OCR success rate ~X%"
  - If disabled: hide entry or show "Currently unavailable" with explanation
- [ ] Verify all states in Chromium (desktop + mobile viewport)

### 5. Tests

- [ ] Unit tests for taxonomy mapping (each exception type → correct category)
- [ ] Unit tests for sanitized error logging (no API keys or secrets in logs)
- [ ] Integration test: trigger each failure category with mocked provider responses
- [ ] Integration test: successful recognition flow unchanged
- [ ] Frontend: Vitest component tests for loading/success/error/retry states
