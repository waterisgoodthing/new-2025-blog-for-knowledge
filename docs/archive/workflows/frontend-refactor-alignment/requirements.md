# Requirements

## Functional Requirements

- FR-01: Produce a source-backed matrix for the supplied refactor-plan, roadmap, note-editor, and Markdown PoC documents.
- FR-02: Classify each material assertion as implemented, partially implemented, planned, historical, contradicted, or unverified.
- FR-03: Define mutually exclusive follow-up task groups for route ownership, editor convergence, visual-system consolidation, and Markdown rendering security.
- FR-04: Record documentation precedence and known contradictions so later work does not execute obsolete instructions.
- FR-05: Preserve the supplied Markdown PoC as a separately approved module.
- FR-06: Incorporate the verified anonymous/public and administrator render-timing probe without promoting local empty-data values to production guarantees.
- FR-07: Define a separately approved session-state optimization group that preserves strict backend authorization while removing anonymous public-page 401 noise.
- FR-08: Define a separately approved production render-readiness group with representative synthetic data, stable DOM/performance markers, and cleanup evidence.

## Constraints

- C-01: Documentation-only changes under this workflow folder.
- C-02: Do not modify src, backend, package.json, lockfiles, database artifacts, environment files, or deployment configuration.
- C-03: Do not mark an implementation item complete without current source and proportionate validation evidence.
- C-04: Do not make a later module executable through approval of this alignment workflow.

## Acceptance Criteria

- The differential matrix identifies the route, editor, sync, visual-system, and Markdown status.
- Each future module has an explicit scope and exclusion boundary.
- The current worktree is rechecked and unrelated user changes remain untouched.
- The final validation record distinguishes static evidence from runtime/browser evidence.
- Runtime probe findings link to independently gated implementation and performance-acceptance task groups.
