# 需求文档：MVP 重构 Spec 任务夹

## 1. 背景

后续重构覆盖 UI 壳层、科目与知识点、题目草稿与题库、错题与复习、附件、
AI/OCR 占位及兼容收口。若缺少严格批次边界，容易出现跨域修改和无法独立验收
的大型 diff，因此需要先建立执行任务夹。

## 2. 使用者

- 项目所有者：审批每批任务与验收结果。
- 后续 Codex：只在当前已批准批次内工作。
- 外部执行代理：通过 spec、checklist 和 handoff 获取相同边界。

## 3. 功能需求

### REQ-01：统一入口

- 输入：附件中的 8 批任务定义。
- 处理：建立总 README 和执行规则。
- 输出：可定位所有批次、依赖与审批门禁。
- 失败处理：缺项时不得称为创建完成。

### REQ-02：独立批次

- 输入：Batch 0 至 Batch 7 的目标、范围、禁项和验收标准。
- 处理：每批生成 `spec.md`、`checklist.md`、`handoff.md`。
- 输出：8 个可单独审批和移交的任务单元。
- 失败处理：内容冲突标记为“待确认”，不自行扩展实现范围。

### REQ-03：顺序门禁

- 输入：当前批执行与验收状态。
- 处理：检查目标、清单、handoff 和用户确认。
- 输出：仅在全部条件满足后允许进入下一批。
- 失败处理：停留在当前批并记录未完成项或风险。

### REQ-04：MVP 边界

- 输入：第一版手工学习闭环。
- 处理：明确 AI、OCR、BKT、完整练习系统等非目标。
- 输出：各批范围不会被误读为全量系统实现。
- 失败处理：无法归属的内容标注“后续批次处理”或“不属于本批”。

### REQ-05：零业务代码变化

- 输入：本轮文档创建任务。
- 处理：只在批准的文档目录写入。
- 输出：业务代码、配置、依赖、迁移和数据均无变化。
- 失败处理：若必须越界，停止并请求用户再次授权。

## 4. 非功能需求

- 可审查：每批边界和验收条件明确。
- 一致性：所有批次采用相同模板。
- 可追踪：checklist 与 handoff 保留执行和确认状态。
- 安全性：不得在文档中建议生产启用认证绕过。
- 兼容性：不得通过规划文档封闭既有公开读取页面。
- 可维护性：使用稳定的 kebab-case 目录名和相对链接。

## 5. 本轮不做

- 不执行 Batch 0 至 Batch 7 的实现任务。
- 不修改 `src/`、`backend/`、配置、依赖、迁移或静态业务内容。
- 不创建数据表、API、页面或真实 AI/OCR 调用。
- 不运行安装、迁移、服务、构建或全项目格式化。
- 不修改现有 `docs/architecture/`；架构冻结由未来 Batch 0 处理。

## 6. 本轮验收标准

1. `docs/specs/mvp-rebuild/` 结构完整，共有 2 个全局文件和 24 个批次文件。
2. 8 批目标、范围、禁止事项和验收标准均与附件对应。
3. 顺序门禁和用户确认机制写入 `execution-rules.md`。
4. 每批 checklist 初始均为未完成状态。
5. 每批 handoff 均包含要求的六个章节，用户确认默认未勾选。
6. 静态验证结果写入本工作区 `validation.md`。
7. Git diff 证明本轮没有修改业务代码或未获准目录。
