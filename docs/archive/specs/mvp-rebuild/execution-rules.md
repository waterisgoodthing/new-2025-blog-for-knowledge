# MVP Rebuild 执行规则

## 1. 顺序执行

后续所有任务必须按以下顺序执行：

```text
Batch 0 → Batch 1 → Batch 2 → Batch 3
        → Batch 4 → Batch 5 → Batch 6 → Batch 7
```

禁止跳批、并行执行多个批次或提前实现后续批次。

## 2. 进入下一批的门禁

只有当前批同时满足以下条件，才能请求进入下一批：

1. `spec.md` 中的目标与验收标准已经完成。
2. `checklist.md` 全部勾选；阻塞、跳过或延期项必须写明原因，且不得伪装成完成。
3. `handoff.md` 已填写完成内容、修改文件、未完成事项、风险点和下一批前置条件。
4. 验证证据已记录在对应 workflow 的 `validation.md`。
5. 用户在对话中明确确认当前批通过。

没有用户确认，不得进入下一批。

## 3. 单批范围约束

执行某批时只能处理该批 `spec.md` 明确列出的内容，并继续遵守仓库
`AGENTS.md` 的 workflow、架构、权限和验证规则。

发现其他问题时：

- 记录到当前批 `handoff.md`。
- 标注“待确认”“后续批次处理”或“不属于本批”。
- 不跨批修改。
- 不顺手修复。
- 不扩大用户已批准范围。

若实现发现计划必须改变，应先更新对应 workflow 的 design、requirements 和 tasks；
范围扩大时必须重新请求用户批准。

## 4. 禁止一次性实现全量系统

第一版只交付手工学习闭环：

```text
科目 → 知识点 → 题目草稿 → 人工审核 → 正式题库
     → 错题草稿 → 正式错题 → 简单复习项 → 复习记录
```

第一版不做：

- 完整 AI。
- 完整 OCR。
- Capture Router 自动分流。
- BKT。
- 完整练习系统。
- 后台任务真实队列。
- 统计报告。
- 搜索索引。
- 对象存储。
- 云部署。

## 5. 权限与架构底线

- `/mistakes`、`/notes`、`/notes/[slug]`、`/blog`、`/blog/[slug]` 保持公开读取。
- 创建、编辑、删除、上传、AI 和复习操作必须保持管理员保护。
- 错题当前是 `Note(type="mistake")`，不得未经设计审批假设已有独立表或
  `/api/mistakes`。
- 后端权限是真实安全边界，前端 `AuthGate` 不能替代后端校验。
- 不得在生产环境启用 `AUTH_BYPASS` 双 true。

若未来批次的目标数据模型与当前架构冲突，应在该批设计阶段明确迁移或兼容方案，
不得仅凭本 spec 直接覆盖现有模型。

## 6. 每批完成与移交

每批完成后：

1. 更新 checklist 的准确状态。
2. 填写 handoff，列出所有实际修改文件。
3. 记录验证证据和失败项。
4. 未解决问题进入风险或下一轮需求。
5. 等待用户明确验收。

代理不得自行勾选 handoff 中的“用户已确认可以进入下一批”。
